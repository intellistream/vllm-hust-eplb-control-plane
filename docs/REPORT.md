# vllm-hust-eplb-control-plane 项目报告

> 日期:2026-10-02
> 对象:Qwen3.5-35B-A3B,2 × Ascend 910B2,TP2 + 专家并行,vLLM-HUST `0.28.1.post1.dev143` / vLLM-Ascend-HUST `0.25.1rc2.dev125`
> 状态:候选(candidate),**未通过性能准入**。本报告同时记录优势和劣势,结论以实测为准。

---

## 0. 摘要

这是一个把 vLLM-Ascend-HUST 中动态 EPLB(专家并行负载均衡)规划器的一处热点函数,以**独立运行时插件**形式抽取出来的项目。

| | 结论 |
|---|---|
| 机制是否有效 | **有效**。规划函数比原版快 **53 到 79 倍**,输出与原版逐项一致,真机上在 EPLB 子进程里确认生效。 |
| swe 压测是否体现优势 | **没有**。默认配置和窄窗口配置下,吞吐、decode P90、TPOT、E2E 均与不装补丁持平,差异在测量噪声内。 |
| 主进程等待规划结果的时间是否缩短 | **没有**。ON 组反而略长(+4.5% 到 +7.3%),但小于 OFF 两次之间自身的波动,不能解读为变差。 |
| 唯一的正向信号 | 窄窗口下 TTFT P95 低 7.6%,但只有一个指标、两次重复、且无机制解释,**未证实**。 |
| 为什么没有服务层收益 | 推断:`compose` 不是规划耗时的大头。**这一点还没有被分段计时证实。** |
| 一句话 | 一个经过严格验证的、组件级有效的优化;在 2 卡 EP2 的 35B 上没有服务层收益,大规模下是否有价值尚未验证。 |

## 2. 基础改造思路

### 2.1 原 PR 做了什么
补丁实际包含三个互相独立的改动:

| # | 位置 | 做法 |
|---|---|---|
| ① | `EplbUpdator.compute_and_set_moe_load` | 收集到的专家负载复制进一块常驻 CPU 缓冲,不再每次 `.cpu()` 新分配 |
| ② | `EplbWorker.compose_expert_update_info_greedy` | 原来对每个要接收的专家都做一次 `torch.isin` 和 `torch.where`;改成每层先构建一次"专家到发送方 / 持有方"的字典表,再线性遍历 |
| ③ | `EplbWorker.pack_update_info` | 每层各做一次 `numpy().tolist()`;改成跨层 `torch.stack(...).tolist()` 批量转换 |

### 2.2 我们怎么改造
原补丁是直接改源码。这里改成**默认关闭的运行时插件**,并做了下面几件事:

1. **只保留 ②。** ① 和 ③ 在测量后被删除(见 3.5)。
2. **按宿主当前源码重写,而不是套用旧 diff。** 宿主已经漂移:`generate_log2phy_map` 现在带 `tp_size` 参数,旧 diff 里没有。
3. **加了子进程引导。** EPLB 规划器跑在 `multiprocessing` **spawn** 出来的子进程里,全新解释器不会加载 vLLM 插件。第一次真机运行时补丁在子进程里命中 0 次,而规划器用的是原版代码。修法是替换 `EplbProcess._launch_process`,让子进程从一个模块级入口启动:先装补丁,再运行宿主原来的 `worker_process`。这是原 PR(直接改源码)不存在的问题。
4. **保守的守卫。** 每个补丁点先用 `inspect.getsource` 检查预期的源码片段,找不到就拒绝安装并报错,不对不认识的实现打补丁。
5. **开关。** `ENABLE=1` 才安装;`KILL_SWITCH=1` 优先级最高;默认关闭时不导入任何宿主模块。`vllm-hust-ext extension enable` 本身**不会**设置 `ENABLE`。
6. **证据事件。** `EVIDENCE=1` 时输出 `installed` 和 `runtime_effective` 事件,都带 `pid`,用来证明补丁在哪个进程里真的跑了。
7. **测量探针(`probe.py`)。** 独立于补丁开关,记录主进程在 `block_update_q.get()` 处等待规划结果的时间,用来在 OFF 组也能测这个量。

## 3. 验证与成绩

### 3.1 等价性
76 项测试(容器上,含 torch)全部通过(含探针的测试)。其中差分测试把替换版本和宿主原文函数逐字对比,输入覆盖 world 大小 2 到 16、最多 256 个专家、1 到 10 层、未变动的层、冗余专家,要求输出(包括 dict 键的顺序)完全一致。

### 3.2 真机可达性
开启动态 EPLB 的真实服务中,补丁在两个 EPLB 子进程里都报了 `runtime_effective`,进程 pid 正是宿主日志中 "Launched EPLB subprocess" 的那两个。

### 3.3 组件基准(`bench/microbench.py`,CPU,7 次取中位数)
| world | 层数 | 专家变动比例 | 原版 | 补丁后 | 加速 |
|---:|---:|---:|---:|---:|---:|
| 2 | 40 | 10% / 90% | 108 / 721 ms | 2.0 / 12.3 ms | 53× / 59× |
| 8 | 40 | 10% / 90% | 207 / 1442 ms | 2.9 / 18.2 ms | 72× / 79× |
| 16 | 58 | 10% / 90% | 410 / 2470 ms | 6.4 / 32.2 ms | 64× / 77× |
| 32 | 58 | 10% / 90% | 424 / 2596 ms | 7.9 / 37.7 ms | 54× / 69× |

服务中补丁后的规划函数每个变动层约 0.2 ms。

### 3.4 swe-prefix-reuse 压测

**设置。** `swe-prefix-reuse` C8,900 秒窗口,2 芯片,`max-model-len 262144`,未开前缀缓存,无 MTP,动态 EPLB 开启。所有组唯一的区别是插件开关和规划间隔。工作负载用本机重新准备的版本(sha256 `4e62e54e…`),其内容已验证与官方 `8044561f…` 字节级一致,tokenizer fingerprint 不同,已在网站 PR #339 里登记为等价变体。

- **默认间隔**:收集 600 次迭代、规划窗口 50 次迭代。OFF、ON 各一次。
- **窄窗口(敏感性测试,非默认)**:规划窗口 10 次迭代。按 OFF、ON、ON、OFF 的顺序各两次,用来抵消共享主机上的漂移。
- **OFF** 指不装补丁(`ENABLE=0`),其余完全相同,探针两边都开。

**噪声参照。** 窄窗口里同一臂两次之间:输出吞吐差 0.44%(OFF)和 0.09%(ON),TTFT P95 差约 1.1%,**等待均值差 5.9%(OFF)和 2.1%(ON)**。

**解读。**
- **吞吐和 decode P90**:ON 和 OFF 没有可区分的差别。decode P90 在窄窗口的 +2.5% 来自 ON 的两次是 36.72 和 38.24,一次与 OFF 重合、一次偏高。
- **等待时间**:ON 没有缩短,数值略长,但 OFF 自己两次之间的差(5.9%)就比 ON 对 OFF 的差(4.5%)大,所以这是噪声,不能解读为补丁让等待变长。
- **TTFT P95 低 7.6%** 是四个点无重叠(ON 2870 / 2838,OFF 3108 / 3072)的,而且差异大于同臂内波动(约 1.1%)。但:只有两次重复;TPOT P95、E2E P95 没有同向变化;默认间隔下 TTFT P95 持平(-0.27%);没有机制解释。因此**作为"值得关注但未证实"的现象记录,不作为优势**。
- **窗口确实重要**:只要把规划窗口从 50 缩到 10,OFF 的输出吞吐就下降 3.6%,主进程被阻塞的时间占比从约 1.8% 升到约 6.5%(每个 worker,相对约 920 秒)。补丁没有收回其中任何一点。

### 3.5 被删除的两个子机制(测量依据)
| 子机制 | 测量结果 | 处理 |
|---|---|---|
| ③ 批量 `tolist`(`pack_update_info`) | 1.0 倍,无收益。耗时几乎全在 `generate_log2phy_map`(逐元素 `.item()`),不在被批量化的 `tolist` 上。服务中该函数每个周期约 225 ms | 删除 |
| ① 复用 CPU 缓冲(`compute_and_set_moe_load`) | 每次约省 20 µs,而这个调用在服务中要约 18 ms(all-gather 和 manager dict 序列化主导),每个 EPLB 周期一次 | 删除 |

## 4. 优势

1. **规划函数本身大幅加速**:53 到 79 倍,在 EP2 到 EP32、低扰动到高扰动下都成立,服务中约 0.2 ms 每个变动层。
2. **行为等价有严格证据**:差分测试覆盖随机放置,包括 dict 键顺序,不只是功能测试。
3. **发现并修复了运行时补丁进不了 spawn 子进程的问题**,并用带 pid 的证据事件证明修复生效。这是原 PR(直接改源码)不需要面对的问题。
4. **对不认识的宿主安全**:源码标记守卫,找不到预期代码就拒绝,不做推测性补丁。
5. **默认关闭、可一键回退**:`ENABLE` 不设即无任何影响,`KILL_SWITCH` 优先。
6. **证据可审计**:`installed` / `runtime_effective` / `timing` 事件带 pid,配套的等待探针让 OFF 和 ON 可以在同一指标上对比。
7. **做了取舍而不是整包搬运**:用测量证明了原 PR 三个改动中两个没有收益并删除,包更小、更容易审。
8. **诚实的实验设计**:窄窗口按 ABBA 顺序重复,保留噪声参照,所有 6 组数据和脚本随仓库公开。

## 5. 劣势与局限

1. **swe 压测没有服务层收益。** 默认和窄窗口两种配置下吞吐、decode P90 均持平。
2. **主进程等待时间没有缩短。** 补丁省下的时间没有传导到主进程。
3. **原因只是推断。** 我们认为 `compose` 在规划总耗时里占比小(策略计算、`pack`、进程间传递占了大头),但**没有做规划器内部分段计时**,这个解释没有被证实。
4. **只测了小规模。** 只有 2 卡、EP2、35B。原版 `compose` 在 EP16/EP32、58 层下要几秒(微基准),是最可能有收益的区域,但服务层没有验证,微基准是合成数据。
5. **每个配置重复次数少。** 默认间隔每臂 1 次,窄窗口每臂 2 次,无置信区间,没有做 bootstrap。
6. **窄窗口不是默认配置。** 结果只说明"窗口紧时的表现",不能代表生产默认。
7. **未做 dense 负例。** 台账要求的 "dense 模型效应消失" 对照没有跑。
8. **适用面窄。** 必须是 MoE 并且开了动态 EPLB,且规划器慢于窗口才可能受益。
9. **工作负载与官方版本不完全同一。** 内容已验证字节级等价,但本机 tokenizer 的 fingerprint 与官方不同,不能声称 tokenizer 一致。
10. **共享主机。** 压测在一台共享的容器上运行,有漂移风险(用 ABBA 缓解,未消除)。
11. **TTFT P95 的 -7.6% 未解释**,不能作为优势引用。
12. **该组件尚未进入网站组件目录**,如要提交排行榜点,需要先登记。

## 7. 适用场景与后续建议

**可能有价值的场景(推断,未在服务层验证)**:大规模专家并行(EP16/32,数十层 MoE)、PD 分离里的解码实例、负载变化剧烈导致频繁重排、运维为了及时均衡把规划间隔调小的部署。

**在实际工作中判断是否值得上:**
1. 是否开了动态 EPLB。
2. 用等待探针量化主进程被规划器阻塞的时间占比。在本环境默认配置下约 1.8%,这是收益上限;占比很低就不值得做。
3. 分段计时规划耗时,确认 `compose` 的占比。
4. 再考虑是否需要缩小规划间隔。

**后续工作(按价值排序):**
1. 给规划器进程内部分段计时(策略计算 / `compose` / `pack` / 队列传递),把第 5.3 条的推断变成证据。
2. 大规模离线对比:用合成的 EP16/32 负载把整个规划流程原版与补丁后对比(必须标注为离线合成)。
3. `generate_log2phy_map` 是 `pack_update_info` 里真正的耗时大头,可作为单独的候选。
4. 把 TTFT P95 现象再重复几次,确认是机制还是噪声。
5. 补 dense 负例和默认间隔的重复。
